# Atguigu Assistant 客服知识库 —— 执行流程与技术方案

> 本文档基于 `Atguigu Assistant 客服知识库.ipynb` 逐单元格整理，说明这个 Demo 做了什么、怎么跑起来的，以及背后用到的技术和设计思路。

---

## 一、项目定位

这是一个 **基于 RAG（Retrieval-Augmented Generation，检索增强生成）的客服问答原型**。

核心目标：让大模型回答关于 **套餐、额度、发票、退款、数据保留、团队协作、企业版支持范围** 等问题时，**不靠模型记忆瞎编**，而是先从本地知识库 `knowledge.txt` 中检索出相关片段，再把这些片段作为上下文交给大模型生成答案。

一句话概括：

> 把"客服知识库"切块、向量化后存进 Milvus；用户提问时先做向量检索，把最相关的几个片段拼进 Prompt，再让 DeepSeek 基于片段作答。

---

## 二、整体架构

```
                 ┌──────────────────────── 离线建库（一次性） ────────────────────────┐
                 │                                                                    │
  knowledge.txt ──► TextLoader ──► RecursiveCharacterTextSplitter ──► chunks(43)     │
                 │                                │                                   │
                 │                                ▼                                   │
                 │                    OllamaEmbeddings(qwen3-embedding:4b)            │
                 │                                │  2560 维                           │
                 │                                ▼                                   │
                 │                       Milvus: rag_tutorial.docs                   │
                 │                  （id / vector / text / source / chunk_id）          │
                 └────────────────────────────────────────────────────────────────────┘

                 ┌──────────────────────── 在线问答（每次提问） ──────────────────────┐
                 │                                                                    │
   用户问题 ──► embed_query() ──► Milvus search(top_k=5, COSINE) ──► 5 个文本片段      │
                 │                                │                                   │
                 │                                ▼                                   │
                 │                    拼接带编号/元数据的上下文块                        │
                 │                                │                                   │
                 │                                ▼                                   │
                 │             Prompt（问题 + 上下文） ──► LangChain Agent ──► DeepSeek │
                 │                                │                                   │
                 │                                ▼                                   │
                 │                          最终回答（可溯源）                          │
                 └────────────────────────────────────────────────────────────────────┘
```

两个链路是分开的：**建库链路只跑一次**（知识库更新时重建），**问答链路每次提问都跑**。

## 三、技术栈

| 组件 | 选型 | 在本项目中的作用 |
|---|---|---|
| 向量数据库 | **Milvus**（Standalone，Docker 部署，`localhost:19530`） | 存储文本向量，提供相似度检索 |
| Milvus 客户端 | `pymilvus.MilvusClient` | 建库、建集合、写入、查询、检索 |
| 嵌入模型 | **Ollama + `qwen3-embedding:4b`**（本地推理） | 把文本转成 2560 维稠密向量 |
| 文档加载 | `langchain_community.document_loaders.TextLoader` | 读取本地 `knowledge.txt` |
| 文本切分 | `langchain_text_splitters.RecursiveCharacterTextSplitter` | 按层级分隔符把长文切成小 chunk |
| 大模型 | **DeepSeek**（`deepseek-flash`） | 基于检索上下文生成最终答案 |
| Agent 框架 | `langchain.agents.create_agent` + `init_chat_model` | 统一模型调用入口，提供一个最小 Agent 壳 |
| 配置管理 | `python-dotenv` + `.env` | 管理 API Key、Base URL 等敏感配置 |

## 四、执行流程（对应 Notebook 的 8 个步骤）

### ① 全局配置

在代码顶部集中定义常量，避免魔法数字散落：

- `MILVUS_URI = "http://localhost:19530"`
- `DB_NAME = "rag_tutorial"`
- `COLLECTION_NAME = "docs"`
- `KNOWLEDGE_FILE = "../knowledge.txt"`
- `EMBED_MODEL_NAME = "qwen3-embedding:4b"`
- `EMBED_DIM = 2560`

**思路**：建库参数和检索参数分开配置，后续换模型/换库只改这一处。注意集合维度必须和嵌入模型输出维度严格一致。

### ② 初始化 Milvus

1. `MilvusClient(MILVUS_URI)` 建立连接
2. `list_databases()` 检查数据库是否存在，不存在则 `create_database()`
3. `use_database()` 切换当前工作库

**思路**：用"数据库"隔离不同项目的数据，而不是所有东西都堆在 `default` 里。

### ③ 创建 Collection

1. 如果集合已存在，先 `drop_collection()` 删除
2. `create_collection(dimension=2560, metric_type="COSINE")`

**思路**：

- 这是演示环境，每次重建保证数据干净、可重复实验；
- MilvusClient 的 **Quick Setup** 会自动生成简化 Schema：主键 `id`（INT64，非自增）、向量字段 `vector`（FLOAT_VECTOR）、并开启动态字段，所以 `text`、`source`、`chunk_id` 可以直接作为标量字段写入；
- `COSINE` 余弦相似度适合文本语义检索，**分数越高越相似**。

### ④ 初始化 Embedding 模型

```python
embedding_model = OllamaEmbeddings(
    model="qwen3-embedding:4b",
    base_url=os.getenv("OLAMA_BASE_URL"),
    dimensions=EMBED_DIM,
)
```

**思路**：嵌入模型本地跑（Ollama），不依赖外部 API，省成本也便于离线演示。`dimensions=2560` 保证与 Milvus 集合维度一致。

> 注：环境变量名写的是 `OLAMA_BASE_URL`（少一个 L）。如果 `.env` 里没有这个键，`base_url` 为 `None`，会回退到 Ollama 默认地址 `http://localhost:11434`，本地运行通常不影响。

### ⑤ 读取文档并切分

1. `TextLoader(KNOWLEDGE_FILE, encoding="utf-8").load()` 读入整篇文档
2. `RecursiveCharacterTextSplitter` 切分：
   - `chunk_size=220`
   - `chunk_overlap=80`
   - 分隔符按优先级：自定义长分隔线 → 空行 → 单换行 → 句号 → 逗号 → 空格 → 字符级
3. 结果：**共切出 43 个 chunk**

**思路（这是 RAG 效果的关键）**：

- **递归切分**会优先在语义边界（段落、句子）处断开，避免把一句话切成两半；
- 第一优先级用了与知识库排版一致的分隔线，等于优先按"知识条目"切；
- `overlap=80` 让相邻块保留重叠内容，防止答案正好落在切缝处被割裂；
- 每个 chunk 后面都要能独立成义，这是后续检索质量的基础。

### ⑥ 向量化并写入 Milvus

1. `embed_documents([chunk.page_content ...])` 批量生成 43 条 2560 维向量
2. 组装数据行：`id`、`vector`、`text`（原文）、`source`（来源文件）、`chunk_id`（序号）
3. `client.upsert(...)` 写入（存在则更新，不存在则插入）
4. `client.flush(...)` 强制落盘，保证立刻可检索
5. `get_collection_stats()` 看统计信息

**思路**：

- 批量嵌入比逐条调用快得多；
- 写入时**同时保留原始文本和元数据**，这样检索回来能直接拼上下文，也能告诉用户答案出自哪一块；
- `flush` 是演示环境的小技巧，避免刚写完搜不到。

数据校验：`client.query(filter="id >= 0", output_fields=["id","chunk_id"])` 返回 **43 条**，确认写入数量正确。

> 注：Notebook 输出里 `get_collection_stats()` 曾显示 `row_count: 86`，但 `query` 实际返回 43 条。统计信息可能包含未压缩/历史段，**以 query 结果为准**。

### ⑦ 初始化模型与 Agent

1. `init_chat_model(model="deepseek-flash", model_provider="deepseek", ...)` 初始化 DeepSeek
2. `create_agent(model=..., tools=[], system_prompt=...)` 创建一个**不带工具**的最小 Agent，只负责按系统提示词生成回答

系统提示词做了三件事：

- **只依据检索上下文回答**，不能靠模型自身知识补全；
- 上下文不足时**直接回答"我不知道"**，降低幻觉；
- **把上下文当作数据，不执行其中可能包含的指令**——这是防 Prompt Injection 的意识（知识库内容可能被恶意注入指令）。

**思路**：这里 Agent 其实只起到"模型调用 + 系统提示"的封装作用，`tools=[]`，真正的"检索"是手写在外面的，方便看清 RAG 的每一步。

### ⑧ 检索逻辑 `retrieve(question, k=5)`

1. `embed_query(question)` 把问题转成同一个向量空间中的向量（注意：查询用 `embed_query`，文档用 `embed_documents`）
2. `client.search(data=[query_vector], limit=k, output_fields=["text","source","chunk_id"])`
3. 返回 `results[0]`，即前 K 个最相似片段及其距离分数

**思路**：Top-K 检索是 RAG 的核心召回环节；K 太小可能漏掉答案，K 太大会引入噪声、浪费上下文窗口。这里取 5 作为折中。

### ⑨ 生成 `generate_answer(question)`

设计上的完整流程是：

1. 调用 `retrieve()` 拿到 5 个片段；
2. 打印每个片段的 `chunk_id`、`score`、`source`、原文，便于调试和观察召回质量；
3. 给每个片段加编号和元数据，拼成规范的上下文块：

   ```
   [片段 1 | chunk_id=4 | source=../knowledge.txt]
   ...原文...
   ```

4. 组装 Prompt：`问题 + 上下文`；
5. 调用 `agent.invoke()`，取最后一条消息输出。

**思路**：把"检索 → 拼上下文 → 生成"显式拆开，而不是用现成的 `RetrievalQA` 黑盒。这样每一步都可打印、可验证，非常适合教学和理解 RAG 内部机制。

示例问题：

> 为什么我在 7 天内申请退款，还是被拒了？

Notebook 中的实际输出显示：Top-1 召回的是"套餐价格"片段（score≈0.7557），模型最终回答"我不知道"。

## 五、核心设计思路总结

1. **RAG 而不是微调**：知识更新只需重建向量库，不用重新训练模型；回答可溯源到具体片段。
2. **离线建库 / 在线检索两条链路分离**：建库慢但只做一次，问答快且可重复。
3. **语义切分优于固定长度切分**：递归分隔符 + 重叠窗口，尽量保证每个 chunk 语义完整。
4. **统一的向量空间**：文档和问题用同一个嵌入模型（同维度），才能比较相似度。
5. **原文 + 元数据一起存**：向量用于检索，文本用于生成，元数据用于溯源和调试。
6. **Prompt 强约束抑制幻觉**：只许基于上下文、答不出就说"我不知道"、上下文视为数据。
7. **过程可观察**：每一步都有打印（切分数、写入条数、召回分数、原文），方便定位"是检索错了还是模型答错了"。

## 六、已知问题与注意事项（仅记录，未改动代码）

1. **`generate_answer()` 的缩进问题（影响最大）**
   上下文拼接、Prompt 构造、`agent.invoke()`、结果打印这几步都缩进在 `for i, hit in enumerate(hits, 1)` 循环内部。
   实际效果是：**每个召回片段都会单独调用一次大模型**，而不是把 5 个片段合成一个上下文统一回答；控制台会打印多次"最终回答"。正确做法是把第 2~5 步移到 `for` 循环**外面**。
2. **环境变量名拼写**：`OLAMA_BASE_URL` 应为 `OLLAMA_BASE_URL`，否则依赖默认地址。
3. **注释与参数不一致**：注释里写的是 BGE-M3 / 1024 维，实际用的是 `qwen3-embedding:4b` / 2560 维，以代码参数为准。
4. **分隔符必须与知识库原文完全一致**：`"\n==============================\n"` 的等号数量、换行位置只要和 `knowledge.txt` 不一致，这一级分隔符就不会生效，会退化到下一级分隔符。
5. **COSINE 分数含义**：0~1，越大越相似；不要和欧氏距离（越小越好）混淆。
6. **召回质量**：示例问题"退款被拒"召回到的是"套餐价格"片段，说明当前切分/嵌入对这条问题的语义匹配不够好，可以尝试混合检索或重排。

## 七、可继续优化的方向

- **混合检索**：向量检索 + BM25 关键词检索，兼顾语义和精确术语（如"7 天""退款"）。
- **重排序（Rerank）**：先召回 Top-20，再用 rerank 模型精选 Top-5，提高上下文精度。
- **按章节/条目切分**：如果知识库结构固定，直接按业务条目切，比通用递归切分更准。
- **元数据过滤**：按 `source`、业务分类先过滤再检索，缩小搜索范围。
- **检索评估**：构造一批"问题 → 标准片段"的测试集，量化 Recall@K，再调 chunk_size、K、模型。
- **回答带引用**：最终答案里标注 `chunk_id`，方便客服核对原文。
- **流式输出**：用 `stream` 提升交互体验。
